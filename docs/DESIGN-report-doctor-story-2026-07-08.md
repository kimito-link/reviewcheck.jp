## A. 理想の体験フロー

1. **スコアを見る**（既存セクション1・不変）。店主は「58点」と順位バッジを見て「ふーん、で？」の状態にある。
2. **所見カードを読む**（新設・唯一の追加コンテナ）。数字に名前が付く——「所見: 星の比較差」。続く2〜3文で「いま近くでお店を探している人は、一覧であなたの店と周辺の店の星を見比べています」という**現在形の構造**が語られる。未来の脅しではなく「自分の与り知らぬところで今日もこの比較が起きている」という事実で、他人事だったスコアが自分の店の話になる。
3. **保健指導3行を読む**。①今日できる無料セルフケア（テキストのみ・売らない）②専門家の見立て＝「すぐ下の緑のボタン」③経過観察＝「ページ下部の月次モニタリング」。選択肢が3つあり、どれも選ばない自由があることが分かる。
4. **視線がそのまま LINE主CTA に落ちる**（既存セクション2・不変）。所見名が付いたことで「この画面のスクショを送るだけで『最初に直すべき1点』をお答えします」という既存リード文の意味が具体化する——**送るべきものに、いま名前が付いたから**。所見カードは LINE CTA の直前で説得を完成させる前座であり、CTA の競合ではない。
5. 以降は既存の流れ（痛み→希望→競合比較→…→月次モニタリング）を従来どおり読む。所見カードの「関連して読む場所」の一文が、15セクションの読み順の目次として機能する。

**情報過多への正面回答（会議批判役の必答論点）**: 所見カードは「16個目のセクション」ではなく**診断書の表紙**である。役割は情報の追加ではなく既存15セクションの束ね直しで、(a) 主所見1つだけが画面全体の「今日の主題」を宣言し、(b) 各所見文が「詳しくは下の◯◯」と既存セクションを名指しして読み順を与え、(c) 副次的な測定事実は判定語なしの事実チップ最大2件に圧縮する。追加コンテナはこの1つで打ち止め（糸マップも P1 でこのカードの内部折りたたみに入れる。カードの外には何も足さない）。

### C-2. selectReviewFindings の優先順位と複合条件ルール（必答論点1）

**裁定: 厳格な単一優先順位（主所見1つ）＋判定語なしの事実チップ最大2件。複合所見文の合成はしない。**

優先順位 K1→K2→K3→K4→K5 の根拠は、来店検討者の閲覧ファネルと抑止の強さ:

1. **質の差は量の差より強い**（K1・K2 が先）。検索一覧で最初に目に入るのは星の数字。同じ一覧で「星4.4・12件」と「星3.7・200件」が並んだとき選ばれやすいのは前者で、低評価の比率は星の質を内側から下げている当事者。よって星差（K1）＞低評価比率（K2）。
2. **量（K3）はその次**。件数も一覧で見えるが、質が並んだときの比較材料。
3. **対応（K4）と鮮度（K5）は詳細画面まで進んだ人にしか見えない**。ファネルの後段なので後置。ただし詳細まで来た人＝来店に最も近い人に効くため、チップとしては必ず拾う。

複合成立時（例: 会議批判役の「件数少×返信なし×ネガあり」）の挙動: K3 が主所見、K4 がチップ「お店からの返信: 確認できず」。ネガ口コミの中身は所見辞書の条件に**使わない**（§D-1）ので、既存 ReviewInsights がそのまま担当する。チップは slate トーンの事実表示のみ（色判定なし・説明文なし）で、二重警告にならない。

戻り値: `{ primary, secondary }`。`secondary` はマッチ順（＝優先順）で最大2件に切る。

### C-4. 糸マップ（P1）: ノード/色の対応表（必答論点2）

構造（partnership §2-2 の同型・モバイルは縦積み・自前SVGまたは flex+CSS、外部ライブラリ禁止）:

```
[近くでお店を探す人] → [Googleマップで候補を比較] → [参照される材料] → [候補に残る・外れる]
                                                    ├ 星評価
                                                    ├ 口コミ数
                                                    ├ お店の返信
                                                    └ 最新口コミ
```

色付け対応表（条件式粒度・**factors の status をそのまま写像**し #score-breakdown の内訳と絶対に矛盾させない）:

| ノード | 実測元 | 色規則 |
|---|---|---|
| 近くでお店を探す人 | なし（行動は実測不能） | 常にグレー |
| Googleマップで候補を比較 | なし（公知の仕組みの説明） | 常にグレー |
| 星評価 | `factors.find(f => f.id === "ratingQuality")` | status good→emerald / warn→amber / bad→red。factor 欠損→グレー＋「未測定」 |
| 口コミ数 | `id === "reviewVolume"` | 同上 |
| お店の返信 | `id === "ownerReplies"` | good→emerald / warn→amber。**status "info" または estimated===true →グレー＋「未確認」**（推定値に色を付けない） |
| 最新口コミ | `id === "freshness"` | good→emerald / warn→amber / bad→red。"info" または estimated→グレー＋「未確認」 |
| 候補に残る・外れる | なし（来店数・心中は実測不能） | 常にグレー |

横断規則: `estimated === true` の factor はステータスに関わらずグレー。エッジ（糸）は常に細い中立線で、色を持たせない。図の添え文（辞書・固定）: 「色が付いているのは今回実測できた材料だけです。グレーの部分は、仕組みの説明であり測定ではありません。」

### C-5. 禁句リスト（新設・osint 実装パターンの写し・自己文脈用）

```ts
  /業界平均|一般的に[0-9]|統計(?:上|的)に/,
  /でしょう|かもしれません|恐れがあります|リスクがあります/,
  /放置する(と|ほど)|今すぐ|お早めに/,
];
export function isFindingBannedFree(text: string): boolean {
  return !REVIEW_FINDING_BANNED_WORDS.some((re) => re.test(text));
}
```

適用範囲: 所見辞書の全フィールド（名前・所見文・構造説明文・セルフケア文・チップ文）＋役割宣言＋治療②③の固定文＋糸マップ添え文。probe スクリプトで全文字列を機械照合（§E）。「〜します」型の未来断定は正規表現で機械判別できないため、辞書追記時に「時制は現在形・主語は構造」のレビュー規約で守る（G-6）。

## D. 偽陽性潰し（fail-closed の徹底）

1. **reviewAnalysis を所見条件に一切使わない（最重要）**。最大5件サンプルの簡易極性判定は「好意的な口コミの誤検知警告」が本番で指摘された前歴（直近 commit 8b97a33・別ブランチ）を持つ。ネガ口コミ由来の所見は作らず、その領域は既存 ReviewInsights に完全委任。flaggedKeywords 等の口コミ由来テキストも所見文に埋め込まない（名誉毀損の再配信防止と同じ回答で二鳥）。
2. **undefined / null は常に「不成立」**。`hasOwnerReplies === undefined`→K4不成立（未確認≠空白）、`daysSinceLastReview` 欠損→K5不成立、`lowRatingRatio` 欠損→K2不成立、`comparison === null`→K1/K3不成立。データ全欠損時は K0（非表示）に決定的に落ちる。
3. **「良好」の誤発報防止**。K6 は `band === "good"` のときだけ。band fair/weak/poor で K1〜K5 が全部不成立なら**何も言わない**（誤った安心も誤った警告も出さない）。
4. **少母数で比率を語らない**。K2 は `reviewCount >= 10`、K3 は `avgReviewCount >= 10`、K1 は `total >= 3` のガード付き。
5. **境界値の確定**（probe で照合）: ratingDiff −0.3 は成立・−0.29 は不成立／lowRatingRatio 0.21×9件は不成立・0.21×10件は成立・0.2 ちょうどは不成立／reviewCount = avg×0.7 ちょうどは不成立（`<`）／days 179 不成立・180 成立。全数値比較は `Number.isFinite` 前提。
6. **isMock は全レイヤー非表示**（デモ注記併記より安全側。既存の「isMock で LINE CTA を消す」流儀と同じ）。`reviewCount === 0` も非表示（星もゼロ件の平均で無意味なため名付けない）。
7. **既存表示との矛盾防止**。糸マップの色は factors.status の写像のみ（独自再判定をしない）ため、#score-breakdown の内訳と食い違う可能性が構造的にゼロ。

## F. 捨てた案と理由

1. **複合所見文の動的合成**（「件数が少なく、返信もなく…」）: 組合せ爆発で禁句CIと probe 網羅が壊れる。全文が辞書の静的文字列であることが景表法・名誉毀損防御の土台なので、単一主所見＋事実チップに置換。
2. **reviewAnalysis を所見条件に使う**: 5件サンプルの誤検知前歴（8b97a33）。fail-closed 原則で全面不使用。
3. **LINE主CTAの後に挿入**: 会議理想（所見がCTAの説得力を上げる並び）に反し、所見→治療②の視線直結が切れる。CTA 押し下げの懸念は高さ上限＋StickyConsultCta で受けられると判断し、前置きを採った。
4. **AI健診式の意味色禁止（中立グレー統一）**: 既存画面が FACTOR_DOT 等で判定色を常用中。1画面に2つの色文法が同居すると「同じ赤が別の意味」になり逆に不誠実。既存トーン準拠＋非実測ノードのみ必ずグレー、で折衷。
5. **既存セクションへのアンカー id 追加**（所見文からのジャンプリンク）: 既存JSXを1文字も変えない制約に抵触。既存の #score-breakdown のみ使用し、他は位置の言及で代替。
6. **予後の未来シナリオ文**（「このままだと◯ヶ月後には〜」）: 未来断定＝景表法直撃＋話法違反。既存の「毎月5件ペースなら約Nヶ月」は既存文言として不変だが、新レイヤーでは一切真似ない。
7. **糸マップの P0 昇格**: 会議裁定（所見カード優先・糸マップ第2弾）を再検討したが維持。文章の構造説明文だけで話法は完結し、スクロール長・工数の増分に見合う追加価値は折りたたみ表示では小さい。
8. **所見の複数枚カード表示**（マッチ全件を並べる）: 15セクション画面の情報過多を悪化させ「束ねる要約」という存在理由を自壊させる。

## G. 地雷と回避策（実装手順に落とした形）

1. **既存を1文字も変えない**: 差分は §C-6 の新規4ファイル＋既存2ファイル各1〜2行のみ。monitoringHref 組み立て・buildLineConsultMessage・スコア帯出し分け・PRIORITY_LABEL/FACTOR_DOT には触れない。実装後 `git diff --stat` で対象外ファイルが混ざっていないことを確認してからコミット。
2. **他者作業との衝突回避**: stash 退避中の作業が ReportView.tsx の70〜110行付近を触っている。挿入は import 群末尾（16行目付近）と297/299行のセクション境界のみ＝衝突しても resolution が自明。作業は `git fetch && git switch -c feat/report-doctor-story origin/main` から（本設計時点で作成済み・クリーン）。ローカル working tree の未コミット変更に触れない・巻き込みコミットしない。git add は個別パス厳守（-A / . 禁止）。
3. **表示文言は全て辞書由来**: FindingCard に文字列リテラルを直書きしない（役割宣言・治療②③の固定文も findings/index.ts に定数として置く）。LLM 生成なし。禁句は §C-5 の新リスト（osint の禁句はそのまま流用しない——「スコア」「診断結果」「改善」は自己文脈なので使用可）。
4. **名誉毀損の再配信防止**: 口コミ本文・flaggedKeywords・aspects 名を所見レイヤーに一切出さない（件数・有無すら使わない設計にしたので、実装で「ちょっと足す」をしない）。
5. **景表法**: 未来断定・確率%・幻の統計・業界平均風の数値は辞書に存在しない状態を probe で機械担保。辞書に文言を足すときは probe に文字列を追加してから（追加漏れは probe が辞書オブジェクトを直接走査する実装にして構造的に防ぐ）。
6. **時制規約**: 辞書追記の PR には「現在形のみ・主語は構造・未来断定なし」のセルフチェック1行をコミットメッセージに残す（機械判別不能な「〜します（未来）」の守り）。
7. **isMock / null 完走**: ゲートとK0 により、mock・全欠損・comparison=null・reviewAnalysis=null のすべてで例外なく「非表示」に落ちることを probe ケースに含める。
8. **検証環境**: テストランナー無し。`pnpm typecheck`＋`npx tsx scripts/probe-findings.ts` が受入の全部（§E）。probe は CI が無くても手元実行を実装完了条件にする。
9. **core 増築流儀**: `packages/core/src/findings/` 新設＋index.ts へ export 1行のみ。既存モジュール（scoring/reviews/osint）への変更ゼロ。糸マップが参照する factors は `DiagnosisResult.factors` を読むだけで、scoring 側に新フィールドを求めない。
