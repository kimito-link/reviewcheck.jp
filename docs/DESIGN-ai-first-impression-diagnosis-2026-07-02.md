## 0. 設計原則（一句）と全体フロー

### 設計原則（一句）

**バズらせるのは「AIの回答」という実測の事実、売るのは「見られ方は毎月変わる」という構造。**

下世話（キャバ嬢適正など）が拡散する心理の正体は「新しい鏡で自分を見たい」＝自己関与＋覗き見。同じ心理を、**「あなたの店、AIに聞くとこう答えられている」という誰も見たことのない鏡**で置き換える。AIの回答は本物の事実（実測）なので景表法の逃げ道が構造的に確保され、しかも「AIの回答は毎回・毎月変わる」という性質そのものが、月額監視サブスクの商品論理（1回直すではなく毎月見続ける）に直結する。**皮＝AI回答の実測、中身＝既存の監視商品が見張る対象（評判・サイト・セキュリティ）のスコア化。** 皮と中身が別物の「2段構え」ではなく、1つの診断の中で皮と中身を層にする。

補助原則3つ:
1. **スコアは決定的、AIは素材**。採点はすべて「公開データ＋構造的チェックリスト」の決定的ロジックで行う。LLMは「回答の実測サンプルを取得する測定器」としてだけ使い、採点者にはしない（再現性・幻覚・景表法の三重防御）。
2. **無料は「事実と存在」まで、具体は LINE の見立てから**。antispy 転用のぼかしは「何が悪いか（項目と件数）」は見せ、「具体的に何が・どこが」を隠す。これが既存LINE設計の交換条件（スクショ→見立て1点）にそのまま接続する。
3. **新規実装はAIプローブと1ページのみ**。入力フォーム・スコアUI・シェア・stateless レポートURL・LINE定型文コピー・/monitor 橋・ref 伝搬は全部既存流用。

### 全体フロー（既存導線への接続点を明示）

```
[SNSシェア/記事(SEO)/紹介リンク(?ref=紹介コード)]
        ▼
[診断入力] reviewcheck.jp 新ルート /ai-check（DiagnoseForm 流用・店名 or URL）
        ▼
[結果ページ] /ai-report/[id]（stateless・encodeReportId 拡張）
   総合スコア円グラフ + 5項目バー + AI回答の実測（一部ぼかし）
        │
        ├─① SNSシェア（ShareReport 流用・シェアURLに via= を付けて拡散を測る）→ 受け手が診断 → ループ
        │
        ├─② LINE CTA（感情ピーク配置・定型文コピー→lin.ee）
        │     → 既存LINE設計のテンプレ0→A→C→D がそのまま受ける（台本に AI診断文脈の差分だけ追記）
        │     → テンプレDの /monitor?plan=…&ref=RVCHK&from=line&utm_source=line（既存・不変）
        │
        └─③ 監視直行 CTA「この見られ方を毎月見張る」
              → /monitor?plan=reviewcheck&ref=RVCHK&from=aidiag&utm_source=aidiag
        ▼
[Stripe 決済 → 契約・監視対象 自動作成（ref=RVCHK webhook・既存不変）→ 継続報酬＋アフィリ]
```

接続の要点: **診断の結果末尾から先は1行も作り直さない**。②は LINE導線設計（フェーズA/B）の入口が1つ増えるだけ、③は /monitor の from 値が1つ増えるだけ（上位設計 P0-1 の分岐条件 `from ∈ {check, line}` に `aidiag` を足す1条件）。ref=紹介コードは reviewcheck の既存伝搬に新ページが参加する（アフィリの「無料診断を配るだけ」の弾が1つ増える）。

## 1. 第1弾の診断（主役）: 「お店のAI第一印象診断」

**ジャンル**: あなたの店・会社が「AIとネットにどう見られているか」を実測＋公開データで採点する総合診断。素材のS層「Webプレゼンス総合健全性診断」（統括1位）の**中身**に、C層「デジタル露出診断」（最バズ枠）の**心理**を、「AI回答の実測」という新しい皮で被せたもの。S×Cの交点として新規提案。

### なぜこれか（4つの根拠）

**(a) バズる心理 — 下世話の代替になる拡散力の根拠**
- **誰も見たことのない鏡**: 店主はGoogle検索での自分は見た（エゴサ済み）が、「AIにおすすめを聞いたとき自分の店が出てくるか／AIが自分の店を何と説明するか」は見たことがない。既知の鏡（検索）より新しい鏡（AI）は覗きたくなる。antispy の「自分の露出度を知りたい」と同型の自己関与で、下世話性ゼロで成立。
- **スクショ栄えする実測回答**: 「AIに聞いてみた」出力のシェアは定着した投稿様式。診断結果に「AIはあなたの店をこう紹介しました/紹介できませんでした」という**引用可能な現物**が入るため、スコア数字だけの診断よりシェアの絵になる。
- **恐怖が本物**: 「AI検索に自分の店が存在しないことになっていた」「営業時間を間違って案内されていた」は実在現象で偽の煽り不要。緊急性は本物の事実だけ、を満たす。
- **横のつながりで転がる**: ローカルビジネスは商店会・同業コミュニティの横接続が強く「お前の店もやってみ」の第二者拡散が起きる。
- **時事の追い風**: AI検索シフト（AIO/LLMO）は2025〜26のメディア文脈に乗る（→記事化・検索流入と両輪 §3）。

**(b) 本業接続 — 5項目中4項目が監視商品の対象そのもの**
スコアの中身（§2）は 口コミ評価・検索の見え方・サイト健康・なりすまし＝**既存の月額監視（サイト・評判・セキュリティ）が毎月見張る対象そのもの**。診断が開けた不安に対する解が、そのまま既存商品。さらにAI項目は「回答が毎回変わる＝一度直して終わりにならない」という監視サブスク最強の商品説明を診断体験の中で実演する。純バズ（占い・キャバ嬢適正）が持てない性質。

**(c) 作りやすさ — 新規はAIプローブ1本とページ1枚**
- 口コミ項目 = reviewcheck の `diagnose()` 既存ロジックそのまま。
- サイト健康項目 = web-health-check-app の `/api/site-health`（HTTPS/WWW統一/応答速度/構造チェック・実装済み・公開API）を呼ぶだけ。
- サジェスト項目 = 既存資産 Negative-suggestion-checker のロジック移植候補あり。
- 結果UI = 「スコア円グラフ＋項目バー＋比較」の既存テンプレ型。シェア = ShareReport 流用。レポート永続化 = encodeReportId の stateless方式流用（DB不要）。
- 新規 = AIプローブAPI（安いモデルに固定プロンプト2本・キャッシュ付き）と /ai-check ページのみ。

**(d) 景表法の逃げ方が構造的**
- AI項目は「◯月◯日時点の実際の回答例」という**事実の提示**（予測ではない）。
- 他4項目は公開データ＋構造的チェックリスト由来。
- スコア名は「AI・ネット第一印象スコア」＝**見え方の現状測定**であり、売上・集客の未来予測を一切含まない。断定は全て「〜の傾向/リスク要因が検出」に落とす。

### 対立（バズ軸 vs 接続軸）の解き方
- バズ軸への回答: 下世話を捨てる代わりの同等の拡散力 = **「AIという新しい鏡」の自己関与＋実測回答のスクショ性＋時事性**。下世話が使う心理（自己開示・覗き見）と同じ筋肉を、ブランド整合的な素材で動かす。
- 接続軸への回答: スコアの中身は監視商品の対象そのもの。診断→監視の橋は「AIとネットの見られ方は毎月変わる」という診断自身が証明する事実。
- 2段構え（純バズ呼び水→本業診断へ送客）は**採らない**（§6 捨てた案4）。皮と中身を1診断内で層にする方が、流量が割れず・保守が半分で・LINE接客の文脈も1本で済む。

## 2. 診断の詳細設計

### 2-1. 入力
- **店名/会社名（＋任意で地域）または サイトURL**。reviewcheck の DiagnoseForm 流用。
- データ源はすべて公開データ（Google口コミ・検索サジェスト・公開ページ外形チェック・LLMへの質問の実測）。**ログイン・スキャン・個人情報は一切求めない**（「パスワード等は不要です」を明記＝LINE設計テンプレ0と同じ防御文）。
- **対象は事業体のみ**。入力が個人名らしき場合は「店舗・会社名でお試しください」を返し個人診断に踏み込まない（センシティブ属性の不変条件を入力段階で構造的に守る）。

### 2-2. スコア構成（100点・5項目・すべて決定的採点）

| # | 項目 | 配点 | 算出（決定的ルール） | 由来 |
|---|------|------|---------------------|------|
| 1 | **AIからの見え方** | 25 | プローブ①「《地域》で《業態》のおすすめは？」→ 自店が回答に登場=満点/登場せず=0。プローブ②「《店名》はどんな店？」→ 正しい基本情報で説明=加点、誤情報・不知=減点。登場/不登場・記述の有無という**事実の有無**だけをルール採点 | 実測（LLM回答・日時とモデル名を表示） |
| 2 | 口コミ評価 | 25 | 既存 `diagnose()` のスコアを 25点に正規化 | 既存ロジック（公開データ） |
| 3 | 検索の見え方 | 20 | サジェストにネガ系キーワード（既存チェッカー語彙）が出るか（件数で減点）＋公式サイトが特定できるか | 公開データ |
| 4 | サイトの健康 | 20 | web-health `/api/site-health` の issues/warnings/goodPoints を配点変換（HTTPS・WWW統一・応答時間・基本構造） | 構造的チェックリスト（実装済み） |
| 5 | 情報のばらつき・なりすまし兆候 | 10 | 店名表記ゆれ・別ドメインの類似サイト兆候などの軽い外形チェック | 公開データ |

- **サイトが無い店**は項目4/5を「対象外」とし残り項目を按分（0点で殴らない・ブランド毀損防止）。API取得不可も同じ按分ルール（地雷#9）。
- **業界平均比較は「はしご方式」**: ローンチ時は捏造平均を出さず「満点基準との差」「全項目クリア状態との比較」で見せる。自前の診断ログが業種ごとにN件（目安100件）貯まったら「当サービスで診断された同業種の中央値」という**実データの比較**に切り替える。「上位◯%」表示も実データ化するまで封印（景表法リスクの正面回答）。

### 2-3. 出力と、無料/ぼかしの線引き（antispy 転用）

出力レイアウト（既存「スコア＋項目比較」型を踏襲）:
1. **総合スコア円グラフ**（大きく1つ。例 58/100）＋スコア帯の称号（採否は論点。採るなら侮蔑ゼロ: 「AI優等生」「あと一歩」「伸びしろ大」）
2. **5項目バー**（各点数＋1行傾向コメント。「〜の傾向があります」統一）
3. **AI回答の実測カード**（バズの主砲。「2026年7月2日時点・モデル◯◯の回答例」を明記）
4. 結果末尾: LINE CTA ＋ 監視直行CTA ＋ シェア

| 無料で見せる（事実と存在） | ぼかす/LINEへ（具体と処方） |
|---|---|
| 総合スコア・5項目の点数と傾向1行 | 改善の優先順位トップ3と手順 |
| AI推薦チェックの**結果**（登場した/しなかった、という事実） | AI回答の**全文**（冒頭1文のみ表示、続きはモザイク） |
| ネガ系サジェストの**件数**（「2件検出」） | その**具体的キーワード**（ワードはモザイク） |
| サイト健康の項目別合否 | 個別の指摘内容の詳細と直し方 |
| なりすまし兆候の有無 | 疑わしい**具体URL** |

線引きの原理: **不安の「存在」は無料、不安の「正体」は見立て（LINE）**。ぼかし部分直下に既存LINE設計の交換条件文型 —「この結果のスクショをLINEで送ると、ぼかし部分のうち最初に見るべき1点を専門家が無料でお返しします」。LINE設計の無料上限（気づき2＋懸念1＋即効策1）と完全整合（ぼかし全開示は無料でしない。全リストと処方は監視サブスク/有料の価値）。

**AI回答表示の安全フィルタ（重要）**: AI回答に自店以外の固有名詞（競合店名等）や事実断定のネガ記述が含まれる場合、その文は無料画面に表示しない（ぼかし側へ送り、LINE内で人間が確認してから見立てに使う）。AIによる第三者への名誉毀損を自サイトが再配信する事故を構造で防ぐ（§7 地雷#2）。

### 2-4. 結果末尾から既存導線への接続（具体）
- **LINE CTA（主）**: AI回答カード直後とページ末尾の2箇所。文言例（partnership 側に置くなら buttonText=計測IDルールに従い1配置1ユニーク文言）:
  - ピーク: 「**ぼかし部分の"最初の1点"を専門家に見てもらう（無料・スクショを送るだけ）**」
  - 末尾: 「**この診断結果をLINEに保存して、あとで続きから話す**」
  - クリック時に定型文コピー（LINE設計 P0-3 と同型）: `【AI第一印象診断の続き】○○（店名）／スコア58点。ぼかし部分の見立てをお願いします。`
  - 窓口ルーティング: 既定は**風評窓口**（診断の物語が「見られ方」）。項目4/5が最弱かつ重大（HTTPS無し等）のときだけIT窓口へ。既存 `lineChannelForTopic` の枠内。**LINE設計 P0-0（2窓口URL）解消済みが前提**。
- **監視直行CTA（従）**: 「**この"見られ方"を毎月見張る（監視プランを見る）**」→ `/monitor?plan=reviewcheck&tier=bamboo&ref=RVCHK&from=aidiag&utm_source=aidiag`。ref=RVCHK は絶対に落とさない（webhook 契約自動作成条件・LINE設計 地雷#7）。
- 色の役割分離は既存踏襲（LINE緑=無料の出口、emerald/amber=申込の出口）。

## 3. バズの仕掛けと検索流入の両立

### 3-1. なぜ友達に見せたくなるか
1. **自己開示が安全**: シェアの主語は「チェックしてみた自分」（既存 ShareReport の思想継承）。低スコアでも「うちの店、AIにまだ知られてなかったw」と笑って出せる自虐で、店の悪評シェアにならない。シェア文固定: `うちの店をAIに聞いてみたら…第一印象スコアは58点でした。あなたのお店は？→`
2. **現物の引用**: AI回答カードがスクショの主役。数字より「AIが実際に言ったこと」が話のネタ。
3. **挑発でなく招待**: 「あなたのお店は？」で締め、業種コミュニティ内の連鎖を作る。
4. **結果画像**: P0 はスクショ文化＋スコア入りシェアテキストで開始。P1 で `@vercel/og` ImageResponse の動的OG画像（スコア円グラフ＋店名＋「AIに聞いてみた」）を追加（reviewcheck は generateMetadata 済み＝画像だけ差す最小改修）。
5. **シェア計測**: ShareReport のシェアURLに `?via=x|line|fb`（1行変更）。シェア経由着地がサーバログで数えられる（§5）。

### 3-2. 検索流入（一過性への保険）
- reviewcheck.jp の既存SEO枠組み（buildMetadata/JsonLd/docs/seo-pages.md）に**業種別記事**: 「美容室がAI検索に出てこない7つの理由」等。記事中腹と末尾に診断フォーム埋め込み（記事=説明、診断=行動）。
- 狙う語: 「AIO 対策」「LLMO 診断」「AI検索 店 出てこない」（需要上昇中・競合薄）。診断名に「AI第一印象」という検索可能な固有語。
- 結果ページは既存どおり indexable（ogType: article）。stateless URL は放流されたレポートURL自体がロングテール入口。
- 記事は月2本×3ヶ月を初期ノルマ案（体制は論点§8）。

## 4. 優先度つきバックログ

共通受入条件: パラメータ無し直アクセスの既存ページの表示・挙動不変。誇大・偽希少性・断定・未来予測の文言を含まない。価格・報酬式・Price ID 不変。既存 buttonText 文字列は1文字も変えない。

### P0（第1弾を最速で出す）
**P0-1【新規・唯一のエンジン】AIプローブAPI**: reviewcheck.jp にサーバルート追加。安価モデル1つに固定プロンプト2本（推薦チェック/認知チェック）。店名正規化24hキャッシュ、レート制限、月次コスト上限（超過時は項目「取得不可・按分」に自動フォールバック）。店名はデータとして扱い（インジェクション対策・テンプレ固定・出力長上限）、回答は表示前フィルタ（自店以外の固有名詞を含む文を除外）。受入: 再診断キャッシュヒット/店名に指示文を入れても崩れない/フィルタ後に自店以外の固有名詞なし/API障害でも診断完走（按分）。

## 6. 捨てた案（次チャットが同じ轍を踏まないため）
1. **下世話系（キャバ嬢適正・星野ロミ原型そのまま）** — ブランド・オーディエンス不整合。代替拡散力はAI回答の実測（§1a）。捨てたのは「下世話」であって「自己開示・覗き見の心理」ではない。
